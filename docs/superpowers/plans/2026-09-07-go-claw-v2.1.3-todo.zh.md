## P0：单 EXE 自动补齐 WebView2 并打开客户端

### 用户合同

同一份标准 Windows x64 产品 U 盘必须同时覆盖“系统已有 WebView2”和“系统没有 WebView2”两类机器。用户只需双击 U 盘根目录的 `GO-CLAW-Portable.exe`：

1. 已安装可用 WebView2 时，直接打开 GO CLAW 原生客户端窗口；
2. 未安装 WebView2 且机器联网时，启动器自动使用 U 盘内的微软官方 Evergreen Bootstrapper 静默安装，验证成功后在同一次启动流程中打开原生客户端窗口；
3. 安装失败、被企业策略阻止或运行时仍不可用时，只回退一次系统浏览器，并显示可定位的错误与日志路径；不得无界重试、假死或启动多个后端；
4. 不要求用户查找、复制或手动运行第二个文件。系统策略要求时允许出现 Windows UAC，但不得主动强制管理员运行；
5. 不改变 portable 数据目录、聊天记录、员工、凭据、额度、账本或在线更新状态。

### 已确认的 v2.1.2 缺口

- 2026-09-07 实际部署的 E/F/G 产品盘只包含 `Portable` 内容，没有 `WebView2` 目录；
- v2.1.2 `clientMode=auto` 在 WebView 构造失败时直接进入浏览器回退，不会安装运行时；
- Full ZIP 中名为 `MicrosoftEdgeWebView2RuntimeInstallerX64.exe` 的文件为 1,783,000 字节，产品元数据是 `Microsoft Edge Update`，实际属于需要联网下载运行时的 Bootstrapper；现有 manifest 将其写成 `evergreen-standalone-x64`，分类不正确；
- 因此 v2.1.2 不能声称“机器没有 WebView2 时，双击根 EXE 会自动安装并打开原生客户端”。用户已确认 v2.1.3 标准交付允许依赖网络安装。

### v2.1.3 实现范围

- 启动器在 `try_build_webview` 前执行有界 WebView2 prerequisite 检查；同时检查 64 位 Windows 的 HKLM 与 HKCU WebView2 `pv` 注册表值，并要求版本大于 `0.0.0.0`；
- 找不到可用运行时时，从 portable 根目录解析 `WebView2/MicrosoftEdgeWebview2Setup.exe`，不得依赖当前工作目录或固定盘符；
- 执行安装器前验证文件是普通文件、位于当前产品根内、SHA-256 与构建 manifest 一致，且 Authenticode 有效、签名主体为 Microsoft Corporation；
- 使用微软合同参数 `/silent /install`，设置有限超时并记录阶段、退出码和安装后检测结果；日志不得包含客户凭据；
- 安装成功后只重试一次 WebView 创建。失败时沿用现有浏览器回退，不重复安装、不重复打开页面；
- Main Build 固定下载微软官方 x64 Evergreen Bootstrapper，增加微软签名、文件身份和实际类型断言，并准确写入 `evergreen-bootstrapper`、`requiresNetwork=true`；不再把约 1.8 MB 的合法 Bootstrapper 误标或误拒为 Standalone；
- 标准产品目录改为让 `Portable` 自身携带 `WebView2`，保证“只复制 Portable 内容到 U 盘根目录”的部署方式不会遗漏 prerequisite；Full ZIP manifest 与 `SHA256SUMS.txt` 必须覆盖安装器；
- 修正 portable README 的旧 `2.0.1` 标题，并生成适用于铺平后盘根目录的 Manifest 路径，禁止继续复制带 `Portable/` 前缀的 Full ZIP Manifest；
- 更新 `START-HERE.zh-CN.txt`、portable README、事实基线、运行时序、维护合同和变更台账。已发布 v2.1.2 资产保持不可变，不原地覆盖。

### 最小测试与验收

- 已有 WebView2：双击根 EXE，确认未启动安装器且客户端窗口正常；
- 干净 Windows 10/11 x64、移除 WebView2：联网环境双击一次根 EXE，Bootstrapper 安装完成后出现客户端窗口；
- 相同机器断网：安装有界失败，只回退一次系统浏览器并给出日志位置；标准联网 profile 不承诺断网原生窗口；
- 非管理员标准账户：验证按用户安装路径；若系统策略阻止，必须有界失败并浏览器回退；
- 安装器缺失、哈希错误、签名无效、安装超时、安装返回失败：均不得执行不可信文件，不得循环或留下多个后端；
- exFAT U 盘换盘符后仍从当前根解析安装器；启动与退出不在系统盘写入 portable 数据；
- Full ZIP/产品盘结构、文件哈希、微软签名和无静态客户凭据合同全部通过。

## SEC-01：New API 8443 公网权限收口

> 状态：2026-09-09 已完成代码、合同测试和生产部署；隔离端口及公网 allow/deny smoke、更新清单摘要、443 billing 边界和 SSH 隧道开关均验证通过。证据见 `docs/incidents/2026-09-08-newapi-registration-attack-investigation.zh.md`。

### 已确认事实

- 现存 Nginx 日志聚合到 `POST /api/user/register` 44 次 HTTP 200 和 2 次 403、`POST /api/user/login` 1126 次请求；New API 业务错误可能仍返回 HTTP 200，不能仅凭状态码统计“成功注册数”；
- 当前 New API 已关闭普通/密码注册，Nginx 已精确拒绝 `/api/user/register`；但公网 8443 的通配 `location /` 仍把其余 New API UI 和 `/api/*` 控制面代理到 loopback 容器；
- 当前 32 个普通 `gc-` 用户全部映射到 32 条 `done` provisioning，未发现仍存活的未映射普通用户；不得因此把所有历史流量判定为无害，也不得自动删除未使用账户；
- 产品盘共享 `PROVISION_HMAC_SECRET` 的局限继续作为已知风险记录，但用户已明确本版本不增加 activation voucher、全局开户/pending 熔断或制盘个性化；
- 不直接开启 Turnstile：当前 New API tag 会把它同时用于 login，而 provisioning 现有建户流程依赖 `/api/user/login`，未经改造会导致合法开户失败。

### v2.1.3 修复范围

1. 在 GO CLAW 仓库新增可审核的 8443 Nginx allowlist 模板：只允许 `/v1`、exact provision/quota、两个 billing enrollment exact 路径和 updates；显式拒绝 `/api/`，其他路径默认 404；
2. 从 8443 移除重复暴露 customer billing/webhook 的宽泛 include；充值和微信回调继续使用现有 443 路由；
3. New API 管理 UI 只经 SSH 隧道访问 `127.0.0.1:3000`；不再允许从公网 8443 直接打开；
4. 变更前备份配置并核对 access log 中的合法路径；先 `nginx -t` 和 staging smoke，再原子切换/reload；失败立即恢复上一配置；
5. 保持 New API 普通/密码注册关闭，并保留 exact `/api/user/register` 403 作为纵深防御；不修改账户、provisioning schema、客户端或产品盘。

### 预计代码和配置落点

- `deploy/nginx/go-claw-newapi-public.conf`：公网 allowlist 与默认拒绝；
- `tests/unit/scripts/test_newapi_public_surface.py`：验证 allowlist、默认拒绝、upstream 路由和 443/8443 边界；
- 运维 smoke 脚本或命令：只验证 HTTP status、upstream 健康和 Nginx 配置，不读取/修改用户数据库。

### 最小验收

- 8443 公网 `/api/user/register`、`/api/user/login`、管理 UI 和未知路径均不进入 New API；`/v1`、provision/quota/enrollment/update 合同路由仍正常，443 充值与微信回调不回归；
- 既有 v2.1.2/v2.1.3 客户端的模型、provisioning、quota、billing enrollment、充值和更新路径全部回归通过；
- New API 后台只能在建立 SSH 隧道后通过浏览器打开；关闭隧道后本机入口失效；
- 本项不产生数据库迁移、不改变新盘格式、不新增 secret，也不影响老用户账户、聊天和额度。

## UX-01：充值后额度展示改为“余额优先”

> 状态：用户已确认“余额数字 + 状态文字 + 充值入口”方案；接口只增 `displayRemaining`，前后端和 UI 已本地实现并通过回归。未改变账本、实际额度、计费公式或轮询频率。

### 当前问题与事实

- 当前服务端严格计算 `granted = remaining + 累计净消耗`、`percent = remaining / granted × 100`；充值增加 `remaining`，历史消耗仍保留，因此充值成功后百分比通常不会回到 100%；
- 该结果没有账务错误，但百分比实际表达“历史累计获得额度中的剩余比例”，用户容易把它理解成“本次充值是否足额到账”；
- GO CLAW 属于随用随充、余额可叠加的模式，没有天然固定的容量上限。单独使用百分比进度条会制造一个不稳定的分母，不适合作为余额的主要表达。

### 推荐方案：剩余算力作为主信息

- 展开侧边栏由“额度 + 百分比”改为“剩余算力 + 紧凑数值”，例如 `剩余算力 5,280万`；大数使用万/亿紧凑显示，悬浮或充值页提供完整整数，不展示美元或 NewAPI 内部单位；
- 不再向用户显示历史累计剩余百分比。细进度条可取消，或仅作为低余额预警色带，不标百分比、也不伪装固定容量；
- 支付到账后立即刷新余额，并短暂显示非阻塞反馈，例如 `已到账 +500万算力`。反馈来自已确认的 `APPLIED` 订单与重新读取的权威余额，不用客户端预测值替代服务端结果；
- 余额充足使用品牌橙或中性色；进入明确低余额阈值后才变红并提示“算力不足，请充值”。阈值需要基于可解释的绝对展示算力，不使用历史累计消费作为分母；
- 侧边栏折叠时显示算力图标和状态点，悬浮显示完整“剩余算力”；点击额度区域进入现有“算力充值”页；
- 充值页保留更完整的当前余额、固定换算与充值记录。侧边栏只承担快速判断“还剩多少”和快速进入充值，不重复堆叠账务信息。

### 已否决的备选方案（保留决策记录）

1. **最近充值基准百分比**：每次充值到账后把当时余额作为 100%，随后按余额消耗下降。优点是充值后符合 100% 预期；缺点是再次充值会重置分母，百分比只代表“自最近一次充值以来”，容易掩盖余额叠加关系，并需要新增可信基准字段；
2. **余额数值 + 历史百分比**：保留当前条形图，但把主信息改为余额，并明确标注“历史剩余率”。改动最小，但仍会引发“刚充值为何不是 100%”的问题；
3. **余额状态分级**：仅显示余额和“充足/偏低/即将用完”，不显示进度条。最容易理解，但阈值必须固定并有产品解释，否则不同模型消耗速度下可能失真。

### 已实施代码与合同修改点

- `scripts/provisioning/provision_server.py`：优先保持现有权威余额和历史百分比计算不变；只有确认需要绝对低余额状态或最近充值基准时，才最小扩展响应字段，禁止修改 NewAPI 额度；
- `src/qwenpaw/app/routers/quota.py`、`console/src/api/modules/quota.ts`：按最终方案透传兼容字段；旧服务端仅返回三字段时仍须正常显示，避免 v2.1.3 客户端更新先于服务端时额度区域消失；
- `console/src/layouts/QuotaBar.tsx`、`console/src/layouts/index.module.less`：余额紧凑格式、展开/折叠形态、低余额颜色和点击充值入口；
- `console/src/layouts/QuotaBar.test.tsx`：覆盖充值后余额增加但百分比不为 100%、万/亿格式、旧响应兼容、低余额状态、到账即时刷新；
- 算力换算继续遵守 `docs/contracts/compute-recharge/`：`￥1 = 500万展示算力`，金额和额度均使用整数，页面不暴露美元或 NewAPI quota unit；
- 不增加新的轮询频率、全量账本读取或启动阻塞。继续复用 `go-claw:quota-updated` 事件和 60 秒常规刷新。

### 验收目标

- 用户充值后第一眼看到“剩余算力增加”和明确到账反馈，而不是依靠是否达到 100% 判断到账；
- 余额数值与服务端权威 `remaining` 的展示算力换算一致，充值、使用和退款后的变化方向正确；
- 老版本服务端、老用户账户、原额度和充值账本不受影响；额度接口暂时失败时保留上一次成功值，不显示伪造余额；
- 不改变充值价格、到账额度、每日限额、退款流程或 NewAPI 计费。
