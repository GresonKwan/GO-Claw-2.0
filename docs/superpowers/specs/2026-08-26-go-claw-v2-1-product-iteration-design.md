# GO CLAW v2.1 产品收敛、桌面启动与 Token Plan 媒体设计

日期：2026-08-26
状态：已获用户逐节确认；2026-08-26 现场 review 后按
`../plans/2026-08-26-go-claw-v2-1-reviewed-execution-plan.md` 修正跨模块合同

## 1. 背景与目标

GO CLAW 已完成在线更新系统的代码、CI 和文档建设。下一次完整 Windows 主线构建将成为新的可信交付基线；该基线验收后，后续产品版本主要通过现有在线更新系统分发。

本轮迭代目标如下：

1. 将 Windows 默认打开方式从浏览器优先改为 Tauri 客户端优先，同时把“窗口存在但页面白屏”纳入失败判定并自动回退浏览器。
2. 收敛客户界面：隐藏“代码”“模型”“数字员工统计”“文件”和语言选择，重新设计左侧底部固定操作区，整体放大字号和图标。
3. 将所有客户可见文字模型选择收敛为“经济、均衡、高性能”三档；允许每名数字员工独立选择，新建员工默认经济。
4. 将现有厂商命名的图片、视频插件改造成两个独立、厂商无关的能力插件，通过 New API 自动路由 Token Plan。
5. 将图片生成和图片编辑默认模型切换为 `qwen-image-3.0-pro`，并按 Token Plan 能力重写媒体工具协议、工具提示词和内容生产员工提示词。
6. 沿用并验证现有更新签名密钥，完成三处公钥一致性、完整 CI ZIP、安装程序、更新包和发布验收流程。

本设计补充并覆盖以下旧决策：

- `2026-08-15-go-claw-runtime-brand-and-batch-credentials-design.md` 中媒体凭证直接指向 DashScope、员工级可选媒体模型以及 Qwen/Wan 客户名称的设计；
- `docs/go-claw-auto-provisioning.zh.md` 中默认媒体模型和百炼直连描述；
- 现有变更台账中媒体模型自动降级到百炼直连的产品行为。

旧的内部兼容标识只在迁移与历史调用兼容层保留，不再进入新用户界面或新对话工具提示词。

## 2. 已确认决策

- 采用产品配置层统一收敛，而不是在各前端组件中分别硬编码。
- Windows 默认采用 Tauri 客户端；Tauri 创建或内容加载失败时自动打开系统浏览器。
- “窗口成功创建”不等于“客户端启动成功”；必须收到正式前端内容就绪信号。
- 不为正常启动设置复杂或刚性的毫秒级预算；就绪检测采用事件驱动，正常路径不得等待失败超时。
- WebView2 使用 Evergreen 共享运行时；完整交付 ZIP 携带离线安装器，暂不固定捆绑整套 WebView2 Runtime。
- 每名数字员工独立保存文字模型档位，新建员工默认“经济”。
- 客户侧只显示三档产品名称和图标，不显示服务商、模型 ID 或模型管理入口。
- 图片、视频保持两个独立插件，分别命名为“图片生成”和“视频生成”。
- 媒体请求链路固定为“插件 → New API → Token Plan”，不新增 GO CLAW 独立媒体网关。
- 不自动回退百炼直连；New API 负责 Token Plan 渠道自动路由。
- 图片生成和图片编辑均默认使用 `qwen-image-3.0-pro`。
- 视频能力按文生视频、图生视频、参考视频分别映射 Token Plan 支持的模型。
- 客户不选择媒体模型；模型映射属于产品配置和 New API 运维配置。
- 媒体协议、工具 Schema、员工提示词和真实 New API 请求均必须测试。
- 下一次正式主线构建产生一个完整 Windows ZIP，并建立可持续使用的更新签名信任链。

## 3. 总体架构

新增一个 GO CLAW 客户产品配置层，作为以下信息的唯一来源：

- 客户模式可见菜单、路由和设置项；
- 三档文字模型的产品名称、图标、说明和传输模型 ID；
- 新建员工默认档位和现有员工迁移规则；
- 图片、视频能力到 New API 模型 ID 的映射；
- 旧插件、旧工具、旧模型到新能力的兼容别名；
- 客户侧固定语言和界面尺寸等级。

前端消费产品名称和展示元数据；后端负责模型白名单、迁移、持久化和调用解析。前端隐藏不是安全或行为边界，后端同样必须拒绝客户模式中不属于三档目录的文字模型，并且媒体插件不得读取用户提交的任意模型 ID。

## 4. Tauri 启动可靠性

### 4.1 现状与问题

当前便携模式的 `Auto` 路径在 `WebviewWindowBuilder.build()` 返回成功后即认为 Tauri 已经启动。该结果只能证明窗口和 WebView 容器创建成功，无法证明：

- 本地 Bootstrap JavaScript 已执行；
- 加载页已经完成首帧；
- 后端控制台导航成功；
- React 根节点已经挂载并绘制；
- WebView2 Renderer 没有崩溃或无响应。

因此“窗口弹出但内部没有任何内容”不会触发当前浏览器回退，这是本轮必须修正的直接架构缺口。历史终端的具体白屏根因在没有完整日志和可复现环境前不作猜测；新架构先补齐分层证据和确定性容灾。

### 4.2 启动状态机

统一安装版和便携版的客户端状态：

```text
process-starting
  → bootstrap-creating
  → bootstrap-ready
  → backend-starting/backend-ready
  → console-navigating
  → console-ready
  → desktop-active

任一 WebView 阶段失败
  → browser-fallback
```

行为规则：

1. 应用启动后立即启动 Python 后端，并创建默认隐藏的本地 Bootstrap WebView。
2. Bootstrap 在本地资源加载、React 加载页挂载且完成首帧后，通过 Tauri IPC 发送 `bootstrap-ready`。
3. Rust 只在收到 `bootstrap-ready` 后显示窗口。用户看到的是品牌加载页，不是空白窗口。
4. 后端健康检查与 Bootstrap 显示并行，不新增串行等待。
5. 后端就绪后，WebView 导航到带桌面标记和缓存破坏参数的正式控制台。
6. 正式控制台在 React 根节点挂载、关键初始状态可读取且完成实际绘制后发送 `console-ready`。
7. 只有收到 `console-ready` 才将桌面客户端标记为成功。
8. Bootstrap 无法就绪、导航失败、正式页面无就绪信号、Renderer 崩溃或无响应时，在后端已就绪的前提下关闭无效窗口并打开系统浏览器；后端自身启动失败进入明确 fatal UI/原生对话框，不打开一个同样不可访问的浏览器。
9. 浏览器回退使用同一后端实例和当前端口，不启动第二个 Python 后端。
10. 正常路径基于事件继续执行，不等待任何失败计时器；具体容灾阈值在实现和真实终端验证中确定，不作为复杂产品预算暴露。

### 4.3 失败诊断与恢复

日志至少记录：

- 启动状态与状态切换时间；
- Tauri、WRY、WebView2 和 Windows 版本；
- WebView 数据目录及其创建结果；
- 导航目标的主机、路径和状态，不记录访问令牌；
- Bootstrap/Console 就绪事件是否收到；
- WebView2 导航错误、Renderer/GPU/Browser 进程错误类别；
- 浏览器回退的触发原因和结果。

不得为了处理缓存损坏而直接删除用户数据目录。允许在证据表明现有 WebView 数据目录不可用时，使用新的版本化数据目录做一次无损重试；旧目录保留供诊断和人工清理。

客户端运行后如果 Renderer 进程失败，应优先尝试安全重载；无法恢复时提示并切换浏览器。失败处理不得留下一个可见但永远空白的窗口。

### 4.4 WebView2 分发

日常运行采用 Evergreen WebView2，以共享系统运行时控制包体和安全更新。完整 Windows ZIP 携带 Microsoft Evergreen 离线安装器：

- 检测到缺少 WebView2 时执行静默的每用户安装，不要求管理员权限作为唯一成功路径；
- 安装失败仍可使用系统浏览器；
- 在线更新包默认不重复携带 WebView2 安装器；
- 只有运行环境策略发生变化时才更新离线安装器。

暂不采用 fixed-version WebView2。固定运行时会显著增加包体并将 Chromium 安全升级责任转移到产品更新流程。若真实日志证明某个 Evergreen 版本存在稳定复现的兼容问题，再通过单独设计评估固定版本。

参考：

- [Tauri Windows Installer](https://v2.tauri.app/distribute/windows-installer/)
- [Microsoft WebView2 Distribution](https://learn.microsoft.com/microsoft-edge/webview2/concepts/distribution)
- [Microsoft WebView2 Process Events](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/process-related-events)

### 4.5 保留 Tauri 的原因

ChatGPT/Codex 与 Claude 当前采用带 Chromium 运行时的 Electron/Chromium 系桌面架构，并不是 Tauri。它们的稳定渲染来自统一运行时、成熟进程恢复以及本地外壳先显示，而不是更小的未压缩安装体积。

GO CLAW 完整包还包含 Python 后端、Python Runtime 和 Node Runtime，应用总大小并不只由桌面外壳决定。本轮不进行 Electron 重写；先通过内容就绪状态机、离线 WebView2 安装和浏览器容灾补齐 Tauri 路径。参考：[Electron Why Electron](https://www.electronjs.org/docs/latest/why-electron)。

## 5. 客户界面收敛

### 5.1 隐藏入口

普通客户模式隐藏：

- 顶部右侧“代码”入口；
- 侧边栏“模型”；
- 侧边栏“数字员工统计”；
- 侧边栏“文件”；
- 设置弹层中的语言选择。

本轮优先从菜单注册表和客户产品配置层控制可见性，不删除底层页面实现。历史深链接和内部诊断可以暂时保留，但不得重新出现在普通导航中。后续若确认无兼容用途，再单独删除路由与代码。

客户版本语言固定为简体中文；设置弹层不显示一个无法实际改变产品语言的控件。

### 5.2 左侧固定操作区

侧边栏分为三个布局区：

1. 顶部员工身份区；
2. 中间独立滚动的功能导航；
3. 底部固定操作区。

底部固定区从上到下放置额度进度、设置按钮和收起/展开按钮。侧边栏内容滚动、窗口缩放或菜单数量变化时，该区域始终固定在左下方。

折叠后隐藏文字与完整额度卡片，但保留可识别的设置、额度状态和展开入口；所有按钮保留足够点击区域和无障碍名称。

### 5.3 尺寸与视觉

- 基础文字、导航文字、说明文字和主要标题统一提升一个产品尺寸等级；
- 侧边栏、模型选择、设置和聊天输入区图标同步提升一个等级；
- 点击区域、行高和控件间距随字号同步调整；
- 不使用浏览器整体 `zoom` 或全局 transform 放大，避免表格、弹层和窄屏断裂；
- 通过产品级尺寸 token 加少量高频页面适配，保留 Ant Design 组件的一致性。

已确认的模型选择图标为：经济使用叶片、均衡使用天平、高性能使用火箭。图标使用真实矢量图形，不以“省、衡、强”等文字代替。

### 5.4 浏览器静态文字光标

应用根节点的非编辑内容使用透明 caret；以下区域显式恢复正常输入光标：

- `input`；
- `textarea`；
- `[contenteditable="true"]`；
- Monaco 或其他代码/富文本编辑器容器。

该修改只隐藏非编辑区域的闪动输入光标，不禁用文字选择、复制、键盘导航或真实输入焦点。

## 6. 三档文字模型

### 6.1 产品档位

| 产品档位 | 传输模型 ID              | 图标 | 说明                                       |
| -------- | ------------------------ | ---- | ------------------------------------------ |
| 经济     | `deepseek-v4-flash-0731` | 叶片 | 默认选择，速度快，适合日常任务和批量处理   |
| 均衡     | `qwen3.7-plus`           | 天平 | 质量与额度消耗平衡，适合复杂分析和内容创作 |
| 高性能   | `qwen3.8-max`            | 火箭 | 提高复杂任务完成质量，但额度消耗更快       |

用户最初提供的 Qwen 名称带有 `qwen-` 前缀；产品传输层使用 Token Plan 和当前 New API 的准确模型 ID `qwen3.7-plus`、`qwen3.8-max`。如 New API 需要额外别名，别名配置在服务端，不进入客户端显示。

### 6.2 选择范围

“全局收敛”表示所有客户可见入口共享同一三档目录，不表示所有员工共享同一个当前值：

- 每名数字员工独立保存档位；
- 新建员工默认经济；
- 切换员工后显示该员工当前档位；
- 在聊天选择器、员工设置、渠道命令和其他客户可达入口中，只能选择三档；
- 普通客户不看到服务商管理或原始模型列表。

后端将产品档位解析为当前模型 ID，保存时同时保留稳定档位键，避免未来更换底层模型时批量重写员工配置。

### 6.3 提醒交互

切换为均衡或高性能时，在选择菜单中显示非阻塞说明。高性能使用明确文案：“高性能模型可以提高复杂任务完成质量，但额度消耗更快。”

切换即时保存，不增加二次确认弹窗。提醒属于信息说明，不应阻碍频繁切换。

### 6.4 现有员工迁移

- 已使用目标模型的员工映射到对应档位；
- 已使用现有 GO CLAW 经济模型别名的员工映射到经济；
- 使用其他模型的客户员工迁移为经济；
- 迁移幂等并记录员工 ID、旧模型 ID 和目标档位，不记录凭证；
- 用户后续手工切换的档位不得被普通启动再次覆盖。

客户模式后端拒绝档位目录以外的新模型写入。内部维护或上游兼容模式可以通过明确的非客户开关保留原模型管理能力。

## 7. 厂商无关的媒体插件

### 7.1 新插件与工具

两个独立插件：

- 插件 `图片生成`：公开工具 `generate_image`、`edit_image`；
- 插件 `视频生成`：公开工具 `generate_video_from_text`、`generate_video_from_image`、`generate_video_from_reference`。

客户可见名称、描述、配置和结果中不出现 Qwen、Wan、HappyHorse、DashScope、模型 ID 或厂商控制台链接。

内部插件目录和 ID 保留不变，以避免重新安装或产生重复插件；它们不作为客户可见名称。
员工工具配置执行下列一次性等值替换：

| 旧工具                   | 新工具                          |
| ------------------------ | ------------------------------- |
| `generate_image_qwen`    | `generate_image`                |
| `edit_image_qwen`        | `edit_image`                    |
| `text_to_video_wan`      | `generate_video_from_text`      |
| `image_to_video_wan`     | `generate_video_from_image`     |
| `reference_to_video_wan` | `generate_video_from_reference` |

员工配置迁移后，模型只看到新工具 Schema。旧工具名不再注册，不新增别名层。

### 7.2 媒体链路

固定链路：

```text
GO CLAW media plugin
  → customer New API media endpoint
  → Token Plan channel routing
  → image/video upstream
```

规则：

- 客户端不保存或直接调用 Token Plan 共享 `sk-sp-*` Key；
- 插件使用当前 GO CLAW/New API 凭证和 New API 基础地址；
- New API 负责渠道优先级、上游 Token Plan 凭证、模型映射和用量记录；
- 不自动回退原百炼直连；
- 旧百炼渠道可由运维保留，但目标 Token Plan 模型不得自动路由到该渠道。

### 7.3 能力与模型映射

| 产品能力     | New API/Token Plan 模型 ID |
| ------------ | -------------------------- |
| 图片生成     | `qwen-image-3.0-pro`       |
| 图片编辑     | `qwen-image-3.0-pro`       |
| 文生视频     | `happyhorse-1.1-t2v`       |
| 图生视频     | `happyhorse-1.1-i2v`       |
| 参考视频生成 | `happyhorse-1.1-r2v`       |

`qwen-image-3.0-pro` 同时支持文生图和一至三张输入图编辑，因此生成与编辑可以共享模型 ID，但必须保留两个工具以区分用户意图和请求体。参考：[Token Plan 个人版模型](https://platform.qianwenai.com/docs/token-plan/personal/token-plan-personal-overview) 与 [图片生成模型](https://platform.qianwenai.com/docs/developer-guides/getting-started/image-models)。

模型 ID 位于产品配置层，不作为插件用户可编辑字段。将来更换默认模型时，通过服务端和产品映射更新，不重新暴露模型选择。

### 7.4 媒体协议保持不变

媒体请求不得复用文字模型的 Chat Completions 请求体。

现有图片适配器继续负责：

- 文本提示词、负向提示词、尺寸/比例和输出数量；
- 一至三张输入图片与编辑指令；
- 已工作的 `/v1/images/generations` JSON 结构，包括编辑时的 `image`/`metadata.images`；
- 同步或异步图片任务响应归一化；
- URL/Base64 输出下载、校验和本地保存。

现有视频适配器继续负责：

- 文生、图生、参考生三类不同输入结构；
- New API `/v1/video/generations` 提交和同路径 task ID 轮询；
- 异步任务 ID、状态轮询、退避、成功、失败和超时；
- 视频 URL 下载、类型校验和本地保存。

本轮不将这些已工作路径换成 `/v1/images/edits` 或 `/v1/videos`，不预先修改 New API。
新默认模型使用现有请求体运行五项真实调用；只有出现可复现的具体失败时才单独诊断。

## 8. 媒体提示词合同

### 8.1 必须清理的旧提示

现有代码中以下内容与新架构冲突，必须同步修改：

- 图片工具声明默认 `qwen-image-2.0`、列出厂商模型并允许员工选择模型；
- 视频工具声明使用 Wan 2.7，并向文字模型承诺时间戳多镜头、音频驱动、视频续写等旧模型参数；
- 插件 Manifest、函数 docstring、注册描述、结果和错误文案包含厂商名称；
- 内容生产员工 `AGENTS.md` 要求调用“Qwen-Image 或 Wan 2.7”并查找 DashScope Key；
- README、默认员工配置、验证脚本和测试合同仍依赖旧插件/工具名称。

### 8.2 新工具提示原则

公开给对话模型的工具说明只描述确定支持的能力和参数：

- 图片生成提示模型提供主体、场景、构图、风格、光线、需要精确出现的文字及画面比例；
- 图片编辑提示模型说明哪些内容必须保持、哪些内容需要改变，并以输入顺序引用“图1、图2、图3”；
- 文生视频提示模型说明主体动作、场景变化、镜头运动和期望时长；
- 图生视频明确输入图片是首帧/参考画面，并描述希望发生的运动；
- 参考视频明确各参考素材的角色或物体身份及目标动作；
- 未被真实 New API/Token Plan 请求合同支持的参数不得出现在工具 Schema 或示例中。

内容生产员工提示词改为：需要实际产出时直接调用“图片生成”“图片编辑”或相应视频工具；凭证和模型由产品统一配置；不得通过无意义试调用探测密钥，也不得伪造生成成功。

## 11. 更新签名密钥

### 11.1 现有密钥验证与保管

现场 review 已确认 GO CLAW 自有密钥存在：本地主私钥、跨磁盘备份、公钥和钥匙串口令均可用，
临时文件经现有私钥签名后能够由仓库公钥和项目 verifier 验证。本轮不生成第二套密钥，也不更改
信任根。路径、Key ID、备份和轮换只由 `docs/GO-CLAW-在线更新签名密钥运维.zh.md` 维护。

### 11.2 三处公钥一致

`tauri.conf.json` 是公钥唯一源码。CI 必须校验：

1. `tauri.conf.json` 的 updater pubkey；
2. GitHub Variable `TAURI_UPDATER_PUBKEY`；
3. 从配置自动复制到完整包的 `GO-CLAW-Config/update-pubkey.txt`。

任一缺失或不一致时，发布构建立即失败，不允许生成可发布清单。

### 11.3 备份与轮换

- 丢失当前私钥将导致已安装客户端无法信任新的在线更新，只能人工完整重装；
- 离线备份应定期验证可解密，但不得在验证过程中打印私钥；
- 密钥轮换需要先用旧私钥签署过渡版本，使客户端同时信任旧、新公钥，再切换 CI 私钥和公开清单；
- 过渡版本覆盖率达到要求前不得停用旧密钥。

## 12. CI 产物

下一次正式 `main build` 暂定发布 `v2.1.0`，产生：

- `GO-CLAW-Windows-x64-Full.zip`：完整冷启动包；
- Windows NSIS 安装程序；
- 轻量在线更新安装包；
- 更新包 minisign/Tauri 签名文件；
- `latest.json`；
- SHA-256 校验文件；
- 构建版本和验证报告。

完整 ZIP 至少包含：

- GO CLAW Tauri/便携启动程序；
- Python 后端和 Python Runtime；
- Node Runtime；
- 前端静态资源；
- 默认客户配置和更新公钥；
- 图片生成、视频生成插件；
- WebView2 Evergreen 离线安装器；
- 凭证示例、使用说明和已确认的低额度本地 `credentials.json`。

Full ZIP 必须包含恰好一份当地 `credentials.json`，不包含 `provision.json`、共享 HMAC、
enrollment ticket 或签名私钥。首次启动直接导入凭证，不运行激活或 sealing 流程。
在线更新资产仍为无凭证白名单 payload，不覆盖客户本地配置。

完整 ZIP 是首次交付、离线恢复和在线更新失败时的标准恢复产物。后续普通更新不重复携带未变化的大型运行时。

## 13. 测试与验收

### 13.1 启动与 WebView

- 安装版和便携版默认进入 Tauri；
- Bootstrap 首帧成功后才显示窗口；
- 正式控制台发送 `console-ready` 后才判定成功；
- 模拟 Bootstrap JS 失败时自动打开浏览器；
- 模拟后端页面导航失败、HTTP 成功但 React 根节点为空、Renderer 崩溃或无响应时自动打开浏览器；
- 浏览器回退复用同一后端；
- 无 WebView2 和无公网环境可使用 ZIP 内离线安装器；
- 普通用户权限、中文路径、空格路径、Windows 10/11 均验证；
- 日志能区分失败阶段且不含敏感信息。

### 13.2 界面

- 顶部不存在“代码”；
- 侧边栏不存在“模型”“数字员工统计”“文件”；
- 设置弹层不存在语言选择；
- 额度、设置、折叠按钮固定在左下方；
- 三档模型均有已确认的矢量图标；
- 字号、图标和点击区域整体提升一个等级；
- 非编辑文字不显示闪动 caret，所有输入框和编辑器 caret 正常；
- 侧边栏展开、折叠、窄屏和滚动布局无溢出。

### 13.3 文字模型

- 新员工默认经济；
- 每名员工独立保存档位；
- 三档分别解析到准确模型 ID；
- 所有客户入口只接受三档；
- 高性能说明文案可见但不阻塞切换；
- 旧员工迁移幂等；
- 客户后端拒绝目录外模型。

### 13.4 媒体工具单元与协议测试

- 图片生成和编辑默认模型均为 `qwen-image-3.0-pro`；
- 文生图、图片编辑、文生视频、图生视频、参考视频请求体快照；
- 图片输入数量、类型、尺寸、负向提示词和输出归一化；
- 视频提交、轮询、成功、失败、超时和异常响应；
- 媒体请求未发送到 Chat Completions；
- 模型名不来自用户输入；
- 旧工具名兼容执行但不暴露给新对话模型；
- 迁移保护用户自定义 endpoint 和提示文件；
- 日志、错误和快照不包含 Authorization Header 或 Key。

### 13.5 提示词合同

- 插件 Manifest、工具 Schema、函数 docstring 和默认员工提示词不包含客户可见的 Qwen、Wan、DashScope 或旧模型名；
- 工具提示只声明当前请求合同真正支持的参数；
- “生成一张图片”选择 `generate_image`；
- “编辑这张图片”选择 `edit_image`；
- “让这张图动起来”选择 `generate_video_from_image`；
- “按这些角色参考生成视频”选择 `generate_video_from_reference`；
- 缺少必要素材时先向用户说明，不虚构 URL 或生成结果。

### 13.6 New API 真实冒烟

发布验证阶段使用最小额度执行五类真实调用：

- 图片生成；
- 图片编辑；
- 文生视频；
- 图生视频；
- 参考视频生成。

核对 New API 记录、Token Plan 扣费/用量和最终结果，并证明请求没有进入百炼直连。真实计费测试只在显式发布验证中执行，不在每次普通 PR CI 中消耗额度。

### 13.7 更新与签名

- 私钥和公钥配对签名通过；
- 三处公钥一致性检查通过；
- SHA-256 和签名任一被篡改时安装被拒绝；
- 下载后和安装前二次验签；
- 更新安装、自动重启、失败回滚和旧版本安装通过；
- 完整 ZIP 内容清单、启动程序和离线 WebView2 安装器通过验证。

## 14. 发布顺序

1. 获得 New API 管理或服务器 SSH 权限，确认当前版本和媒体接口合同。
2. 在 New API 配置 Token Plan 图片、视频模型和渠道路由。
3. 完成产品配置层、界面、模型档位、启动状态机和媒体插件实现。
4. 完成版本化迁移与全量自动测试。
5. 使用现有密钥完成本地签名探针和三处公钥一致性检查；只有探针失败才按既有 bridge 轮换流程处置。
6. 运行正式 `main build`，生成完整 ZIP、NSIS 和更新资产。
7. 在多台 Windows 终端验证冷启动、白屏容灾、媒体调用和在线升级。
8. 发布 `v2.1.0` 完整资产，但暂不更新公共 `latest.json`。
9. 验收通过后发布更新清单，使可信基线客户端按现有六小时周期发现更新。
10. 后续版本复用签名 CI 和在线更新系统，不再依赖人工复制全量目录。
